# M08 financial Core and operation

The first paid execution path uses prepaid USD Kivro Credits. The nine exact price tiers live in PostgreSQL migration `0015_finance.sql`; code selects an enabled tier and copies its buyer price, Kivro fee and seller amount into a job snapshot. Tax is a separate minor-unit field and must be set by a legally approved tax policy before public checkout. No percentage calculation determines an old job's settlement.

## Authoritative flow

1. Server-side Stripe Customer and PaymentIntent operations use the pinned Stripe adapter. A signed webhook is stored in `stripe_inbox` before reconciliation; reconciliation reads the current PaymentIntent/charge/refund state from Stripe. The buyer receives credits only once through a balanced immutable journal.
2. The cloud locks the job and financial accounts in PostgreSQL, checks buyer and seller Connect readiness/freshness, and moves the exact job price from `buyer_available` to `buyer_reserved` in one transaction with the job payment state. M07 dispatch, claim and execution transitions call the Core verifier, which requires this reservation and its exact journal effect. A Worker payment claim has no authority.
3. Only a cloud-finalized `COMPLETED` job with validated durable result may settle. Settlement moves reserved credits to `seller_pending`, platform fee and any separate tax liability exactly once. A terminal failure or eligible pre-dispatch cancellation instead restores the buyer's reserved credits.
4. Seller earnings mature from pending to available after seven days. A durable outbox uses a stable Stripe idempotency key for a Connect transfer. Provider confirmation moves seller available to transferred. A separate reconciled payout moves transferred to paid out. A failed payout after a reported payment creates a compensating entry; the original payout journal remains immutable.
5. Eligible full refunds append compensating entries. After a bank payout, an administrative full refund records platform-funded loss and leaves the historical seller payout intact. Stripe credit refunds and disputes reconcile independently from current provider objects, freeze further paid jobs, and do not erase each other's state.

`financial_journals`/`financial_entries` are append-only, balanced and unique by economic effect. Account balances and seller earnings are reconstructed from entries. `reconcileLedger()` checks balance, reservation and provider-effect consistency. Every Stripe write is idempotent; outbox and inbox processing may safely retry after a process restart.

## Configuration and validation

Set `DATABASE_URL`, `KIVRO_STRIPE_MODE`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` and a random `FINANCE_CRON_SECRET` of at least 32 characters on the server only. `.env.example` explains how to obtain each setting. Do not put Stripe credentials in Worker configuration. Test and live keys/objects may not mix. Run migration `0015_finance.sql` through the repository migration workflow before enabling paid dispatch. The authenticated `POST /api/internal/finance/reconcile` endpoint runs bounded inbox/outbox/provider polling, terminal settlement/release, maturity, transfer and ledger checks. Both deployment profiles must schedule it and alert on nonzero audit discrepancies; that deployment gate remains open.

Run `pnpm test:postgres:m08` for the real PostgreSQL concurrency and state-machine suite, `pnpm test` for Stripe signature/adapter, price and economics unit tests, and `pnpm openclaw:approve-local-image` after any sandbox/runtime source change. The latter approves only the exact local tested Docker image digest. A real signed Stripe test-mode charge, browser purchase, authenticated job route, two-provider paid E2E and external legal/tax review are still open in `docs/verification-backlog.md` and `spec/COVERAGE.md`. The §24.25 P5 direct manual-capture model is a separate open implementation requirement after the prepaid-credit MVP.
