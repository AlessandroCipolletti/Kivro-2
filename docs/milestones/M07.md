## Security/payment risks and sequencing

`paymentSecured: true` in a Worker message is not financial truth. A trusted server-side ledger reservation validator is mandatory before paid dispatch and job execution; M08 provides it. Until then the production paid admission path must fail closed. A cloud state of `PAUSE_REQUESTED` does not mean local execution stopped; only a Worker acknowledgement after container/process-tree control may produce `PAUSED`. A pause that cannot be performed safely must return `PAUSE_NOT_SUPPORTED` or another explicit failure, never silently cancel or claim success. Buyer-visible output remains untrusted until M05 validation and durable private storage finalization.

The M00 sequencing rule applies: M07 implementation-stage completion and full cross-system verification are separate. Graphical seller/buyer controls, payments, real two-profile composition roots, and canonical paid E2E remain open until their named milestones provide the required dependencies. Every deferred row remains in the cumulative backlog with its original acceptance criterion.

The cloud accepts seller PAUSE only from `RUNNING`; a `STARTING` container has no process tree that Docker can yet freeze, so that stage returns `NOT_ELIGIBLE` instead of leaving an unconfirmable request. Cancellation remains available. After a Worker daemon restart, an orphaned container without its former supervisor/broker is stopped before new offers; it is never blindly rerun. Full paid paused-job continuation and cloud reconciliation across a Worker process restart remain M29 verification and must not be claimed from the local restart component test.
