## Adversarial design review before implementation

| Attack or failure | Required boundary |
| --- | --- |
| Model invents capability, price, availability, rating or permissions | Never accept facts from model as authority. Resolve IDs to current public Core documents; code filters, scores and renders actual projections. |
| Seller description/review/result injects instructions | Only bounded sanitized data enters user/tool content. System instructions are fixed. Model tool calls are schema validated and allowlisted; purchase is never a model tool. |
| Buyer asks to spend $15, model requests $16 or retries parallel purchases | Immutable explicit approval, integer minor-unit ceiling, row-level plan lock and per-step deterministic IDs. Reconcile created jobs/ledger after uncertain response. |
| Price/availability/version changes after plan | Requote and revalidate immediately before each purchase; stale or more expensive terms pause for fresh buyer approval. No silent provider substitution in approve-plan mode. |
| Model or provider fails/returns invalid JSON | No job/financial transition before validated plan and explicit approval; bounded retry and fail closed. Classic marketplace stays available. |
| Cross-job file ID guessed or another buyer's output used | Resolve by source job ownership, completed/finalized result manifest and exact mapping. Scoped target-job read grant only. |
| Server restarts mid-purchase or mid-plan | Persist plan, steps, deterministic job/quote/reservation IDs before effects; idempotent reconciliation resumes from authoritative job/payment/result state. |
| Platform AI key/cost mixes with seller inference | Server-only provider adapters and platform usage table; seller Worker contracts contain no platform provider key. |

## Implementation and adversarial reread

M11 now uses public, current-version catalog documents and M09 availability for discovery. The model extracts intent or proposes bounded capability IDs and DAG edges; deterministic Core code checks category, budget, rating, permissions, I/O, runtime, timing, price snapshot, immutable version and file compatibility. Read-only model tools have strict schemas and only public capability data. Internal plan construction is atomic rather than exposing a partially persisted `add_plan_step` mutation: the planner builds all steps, validates the complete graph, then persists one reviewable plan. `request_plan_approval` is the buyer plan-review view and explicit approval route; `execute_approved_step` is the server-only Purchase Authorization Service. Neither operation is available as a model tool. This preserves the §149 internal service contract without granting financial authority to inference.

The platform inference router has provider-neutral requests, task profiles and optional bounded fallback. OpenAI Responses and Anthropic Messages adapters normalize structured output, tool calls, provider errors and usage. Server-side keys never enter Agent API responses or Worker envelopes. Provider configuration changes create an append-only hash audit record on use; usage/reserved-token guards persist before calls, and safe aggregate cost metrics are available to the operator route. Remote health probes check provider APIs, while classic marketplace pages work without inference. No real provider credential exists in this workspace, so live model contract evidence is still open.

The plan repository persists ordered steps, quotes, public permission snapshots, immutable approval revisions and buyer ownership. PAS serializes a plan, rechecks current terms before every purchase, delegates credit reservation to M08/M09, and never trusts a Worker or model with financial truth. Already bought jobs use M07 offers/leases and the M10 buyer service. Reconciliation resumes after process restart. A completed, validated and settled source job can feed scalar output or scoped private file assets into the next job; a fabricated or cross-buyer asset cannot. Independent branches can run within one hard ceiling. After a material change, the plan pauses and shows current equivalent alternatives for a fresh buyer approval. Completed branches retain their charges and provenance after a later failure; unstarted steps are not purchased.

`pnpm agent:scheduler` is the host-native local reconciliation trigger. It calls the token-protected internal Web/API route on loopback, retries after a Web/API outage, and does not depend on a buyer browser. Fresh local setup writes the private token; `pnpm local:agent:setup` adds it once to an older private `.env.local`. M19 must schedule the same route reliably in each deployment profile.

The post-pass audit reread every mapped requirement and source §§120–191 and §§488–517. It found and corrected: a PostgreSQL quote/purchase lock inversion; lost step ordering after database reload; stale plan terms after partial completion; input drafts that needed preapproval contract checks; multiple file outputs into one `FILES` input; PDF intent being confused with PDF source material; a discovery page cap that could falsely say no alternative; missing file-extension matching in output discovery; an extracted synonym that could retrieve but not rank a real capability; and buyer copy that could imply a plan component alone satisfies the final output. M07/M10 asset lookup was tightened so only finalized, settled, same-buyer output can be chained. A three-research-to-PDF DAG and exact maximum budget are validated as an M11 Core fixture. Its real multi-seller paid staging journey remains a mandatory M16 gate.

The AI Request UI exposes current prices, ratings, availability, quote expiry, declared permissions, input/data flow, each job, settled/reserved spend, pause/replan, provenance and private final-job links. It distinguishes recommendation from execution timing and never presents a queue delay as known without evidence. The privacy notice discloses platform provider processing of request text and bounded public metadata, and that private file bytes are not sent to platform inference. Desktop and 390px mobile screenshots are produced by `tests/browser-m10/marketplace.spec.ts` and were inspected; no horizontal overflow or misleading financial state was observed.
