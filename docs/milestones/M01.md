## Implementation plan

1. Define one account/identity model with optional seller activation and explicit Worker-device ownership. Buyer and seller are capabilities of one user, not separate logins.
2. Define normalized versioned input/output contracts, typed values, strict boundary validation and simple conditional fields. The same contract objects must be usable by API, Web and Worker layers.
3. Define internal permission policy and generate a buyer-safe public manifest deterministically. Compare versions for permission expansion; never accept hand-authored trust indicators.
4. Define immutable published capability-version snapshots and pinned job snapshots with no credential values.
5. Define explicit, idempotent job transition rules and transition metadata. Prepare one forward-safe PostgreSQL schema/migration history for both profiles.
6. Test malformed/hostile input, snapshot immutability, permission privacy/expansion, account identity, transition idempotency and invalid transitions. Run architecture, typecheck, lint and build. Keep integration/paid E2E gates open until their dependencies exist.

## Implemented and validated in this stage

- One account schema with optional seller profile and Worker device ownership; account-level eligibility guards do not claim payment or Worker readiness.
- One normalized I/O contract and scalar/asset-reference validator; physical file inspection and ownership remain open for M05.
- Internal permission schema, deterministic public taxonomy and conservative expansion detection; M04 must prove this matches effective sandbox enforcement.
- Separate platform/seller inference credential-reference schemas, canonical fixed USD tier table, immutable draft candidate and published-version/job-snapshot shapes. No production publisher exists yet; a draft cannot create a job snapshot.
- Explicit pure job transition reducer, one PostgreSQL migration history with published-row/job-snapshot immutability, append-only transitions and a database constraint rejecting queued/executing rows without a reservation reference. The reference is not proof of secured payment; M08 must provide authoritative ledger linkage.
- `pnpm typecheck`, `pnpm lint`, `pnpm test` (33 tests), and `pnpm test:postgres:m01` passed. The PostgreSQL test uses an isolated port-free PostgreSQL 16 container and tests unpublished-version denial, unpaid queue denial, published immutability, historical snapshot immutability and append-only transitions.

## Adversarial review

- Candidate generation deliberately cannot publish. `PublishedCapabilityVersionSchema` is an internal future persistence shape, not an authorization token; M03/M04 must prove effective policy before creating it.
- A Worker-supplied `paymentSecured` flag and a reservation UUID are not financial truth. There is no dispatch or execution path. M08 must bind reservation to an authoritative ledger transaction, and M07 must run the transition reducer under database concurrency control.
- URL validation checks syntax only. SSRF protection belongs to M06 Research/Resource Brokers. Asset references are IDs only; M05 must inspect content, ownership, sizes and durable storage.
- The public permission projection is not yet compared with Docker/OpenClaw effective permissions. M04 must block publication and execution on mismatch.
- PostgreSQL JSONB snapshot columns are immutable after publication/job creation, but the application must validate their full runtime schema and provenance before insertion.

M01's 64 mapped IDs remain open for complete cross-system verification. Five overlap M00's backlog; the other 59 have new per-ID rows in `docs/verification-backlog.md`. No M01 ID was marked `VERIFIED` from schemas or isolated tests alone.

## Risks and gates

No runtime validation alone authorizes a job. Payment reservation must be checked from authoritative persisted state before dispatch. Permission summaries must match the effective sandbox policy before publication. File references require M05 content inspection/storage. A pure state transition is not durable until M07 transaction/persistence work. Database/provider conformance requires M19 runnable composition roots. These remain OPEN until tested.
