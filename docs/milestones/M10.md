## Preimplementation adversarial review

| Threat | Required control |
| --- | --- |
| Seller description/review/example contains script or prompt injection | Render as escaped/sanitized untrusted content; discovery document excludes secret/internal fields. |
| Draft/private/retired capability leaks via search or seller page | Server-side visibility and current published-version filter for every public query. |
| Buyer forges job/review/favorite ownership | Session-derived buyer ID; database joins on immutable ownership and settled delivery; unique job review and self-review denial. |
| Historical Run Again silently uses old commercial terms | New current-version quote and explicit confirmation; old snapshot remains immutable. |
| Price, Worker availability or input validity changes after page render | Revalidate Core quote and input at purchase; M08 reservation and M09 admission remain authoritative. |
| Seller-local or another buyer's files appear in results/examples | Only explicitly approved public examples; result assets stay private and retrieval reauthorizes exact buyer and retention. |
| Unsupported preview executes active content | Restrict inline previews to safe MIME, set response headers and use authorized download for other formats. |
| Empty/new marketplace displays invented activity | Show honest empty/unknown states, never fabricated ratings, uptime, duration or testimonials. |

## Adversarial review and evidence

The post-implementation review reread all 148 mapped IDs and Master Spec §§28–29, §§120–161, §§356–368. It found and corrected buyer-visible faults: a Busy badge implied queue admission even when M09 capacity denied it; Run Again/template navigation could retain stale client form state; a lost HTTP response after a committed purchase could cause a second purchase attempt; input-group metadata was not visually represented; and returning buyers needed an explicit changed-version/permission warning. The final browser test verifies the authoritative queue badge, form remount, version warning, and recovery by exact stable job ID. Public example and output Markdown render as escaped text, including script-like content. Seller path/credential patterns are rejected from public metadata and examples, and unpublished or older-version examples are not projected.

`tests/m10-postgres-integration.mjs` exercises visibility/grants, search filters, exact price and snapshot history, categories, favorites, seller profile, examples, private asset ownership, verified reviews and append-only revisions, credit reservation, duplicate purchase, settled result, cancellation and changed-version Run Again. `tests/browser-m10/marketplace.spec.ts` uses real PostgreSQL, Mailpit, auth and pinned SeaweedFS to exercise discover/detail/mobile views, all five M09 availability states, schedule-closed refusal, scheduled purchase/cancel, private upload, failed unauthenticated/foreign access, a lost purchase response, and buyer history. Screenshots are written to `test-results/m10-*.png` for visual inspection; they are local test artifacts, not evidence of Worker output delivery. M07–M09 PostgreSQL, Docker sandbox, private storage and shared unit suites remain regression gates.

The cross-milestone retention audit found that a pre-uploaded buyer file could expire before an accepted job's latest start. M07 late manifest finalization and M09 booking now extend both private object retention and the matching grant through latest start plus permitted runtime, within the job/financial transaction. Migration `0018` keeps grant revocation one-way and permits only bounded active scheduled extensions. The M10 direct upload uses migration `0019`, a staging key distinct from the immutable final asset key, and storage-side copy after double validation. The browser sends binary directly to storage; the application API receives only upload metadata. Staging cleanup after a failed/abandoned upload remains a durable retention/reconciliation gate in M29 and does not make an unvalidated file usable.

The same audit corrected example-asset retrieval: a PUBLIC example is readable by any buyer, an UNLISTED example by its direct link, and a PRIVATE example only by an active grantee. Every example response is non-cacheable and rechecks the current published version. A real SeaweedFS text example download and PostgreSQL visibility matrix cover this boundary. The M08 finance race regression had an overly strict exactly-one-success assertion; offer followed by pre-start cancellation can both succeed while ending CANCELLED with one released reservation. The corrected assertion checks that convergent state and the authoritative reservation rather than assuming thread order.

The M10 mapping in `spec/COVERAGE.md` is 36 narrowly `VERIFIED`, 9 `DEFERRED_VERIFICATION` with complete M10 implementation but a named later E2E/component dependency, and 103 `TODO` assigned to later-owned Agent, seller example authoring/test, or combined product journeys. Fifteen earlier deferred gates now have final M10 Core/browser evidence and are `VERIFIED`. Exact missing dependencies and closing tests for open gates are in `docs/verification-backlog.md`. In particular, the real paid browser→Worker→sandbox→validated result/file return remains M13/M16 work; M10 has a private result route and a component-level finalized result test but does not claim that full journey. Public seller example text/file storage is exercised; image/video/3D media and all MIME preview acceptance still require M16 storage-backed fixtures. AI discovery, recommendation and orchestration are M11 work and remain open.
