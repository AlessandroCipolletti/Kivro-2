## Adversarial design review before implementation

| Attack/race | Required control and test |
| --- | --- |
| Two jobs spend one buyer balance | Lock a buyer financial account in the same PostgreSQL transaction as balanced reservation entries; parallel transactions must yield one success. |
| Forged payment flag or bare reservation row | M07 verifier must check the job-bound active reservation and reconstruct the exact reserved amount from immutable journal entries under a lock. |
| Duplicate purchase/webhook or reordered provider events | Verify raw-body Stripe signature and environment; persist event before dependent work; unique provider object and economic effect keys; reconcile current provider object state instead of trusting delivery order. |
| Retry after DB timeout or crash | Stable idempotency key and single-transaction journal/effect insert; retried result reads original immutable effect. External Stripe writes use durable outbox and the same Stripe idempotency key. |
| Worker claims completion or seller payout | Completion alone is not settlement; require platform `COMPLETED` plus matching finalized durable result. Only cloud financial service can journal settlement/transfer, never Worker payload. |
| Cancel vs offer/claim or release vs settlement | Lock job first for every competing transition, then finance rows. Release before dispatch or after verified terminal failure; dispatch wins means cancellation requires Worker stop evidence. Exactly one terminal financial effect. |
| Price edited after purchase | Persist the snapshot once. Ledger uses that snapshot, not current tier or mutable capability price. |
| Money and cost ambiguity | Safe integer minor units only, USD exact tier table, tax separate; estimated provider cost clearly distinct from measured and unknown; buyer cannot submit guardrail overrides. |
| Unready seller or mixed Stripe modes | Recheck connected-account readiness before paid reservation/dispatch; test and live keys, objects and webhook secrets cannot cross. |

## Implemented financial boundary

- Migration `0015_finance.sql` creates one canonical enabled tier table, immutable per-job snapshots, credit purchase/reservation/payment states, balanced append-only journals, buyer/seller accounts, seller transfers/payouts, actual processor-fee, refund and dispute effects, plus durable Stripe inbox/outbox. PostgreSQL constraints and triggers reject journal edits, unbalanced effects and duplicate economic identities.
- Shared finance policy and `PostgresFinanceRepository` own the state machine. The M07 `PaymentReservationVerifier` now checks the job-bound active reservation, exact immutable reserve journal, matching buyer/price, active buyer billing and recently reconciled seller Connect state at every paid execution boundary. The Worker cannot create that proof.
- Stripe adapter owns Customers, SetupIntents/payment methods, credit PaymentIntents, Connect account/onboarding, transfer/reversal, payout, refund/dispute and actual processor fee reads. It pins an API version and mode, uses idempotency keys, and never enters the Worker package. Raw-body signed webhook ingestion persists before provider-state reconciliation. An authenticated internal cron endpoint invokes bounded reconciliation.
- Validated durable output is the only settlement trigger. Failure/cancellation releases reserved Credits; full refund creates compensating entries. Seller pending earnings mature after seven days, then transfer and payout are separate idempotent provider transitions. Provider spend is separately measured, estimated or unknown; immutable seller limits cover model, calls, tokens, spend and OpenClaw tools.

## Adversarial review against Master Spec §§24–25 and 278–298

The final review retraced the entire credit and seller-money path from an authenticated Stripe object through journal funding, job reservation, M07 offer/lease checks, cloud result finalization, seller maturity, transfer and payout. Concurrent account locks plus unique effect keys prevent double spending and duplicate settlement. The reviewed denial cases include forged payment flags, bare reservation records, Worker-supplied earnings, duplicate completion, invalid output, release/settlement race, cancellation/claim race, webhook replay/reordering, Stripe mode mixing, stale Connect state, transfer timeout/retry and changed tier after purchase. The review found and fixed two M08 defects: an uppercase Stripe object ID was rejected by the adapter path validator, and a dispute arriving after a card refund could overwrite the purchase's refund state. The latter now preserves the refund state; PostgreSQL regression tests cover it and a paid-then-failed payout reversal. A deferred PostgreSQL constraint and test also reject a journal with zero entries, rather than relying on the reconciliation audit to discover it later.

The review also corrected an evidence overclaim: `PAY-0023` is the direct PaymentIntent flow's dispatch step, not the prepaid-credit dispatch step. It remains open with the future §24.25 P5 direct-payment implementation. No credit-path test is used to mark that direct-path requirement verified. Stripe test-mode network behavior, merchant-of-record/tax/stored-credit terms, buyer/seller purchase UI, deployed scheduler, two-profile conformance and M26 crash-window faults remain mandatory and open.

## Remaining boundaries

Paid Core execution is enabled only when the finance repository is wired as M07's mandatory verifier and the specific job has an exact, active, recently reconciled reservation. The current web application has no authenticated buyer purchase/job API and no deployed paid buyer-to-Worker path, so deployed paid execution is still unavailable and must not be represented as an accepted end-to-end flow. Both Netsons and AWS production composition roots, live Stripe test-account evidence, real scheduled reconciliation and browser purchase/earnings surfaces arrive in later milestones. Public launch also requires legal/tax/credit-policy review. These are tracked as open work, not as verified M08 claims.
