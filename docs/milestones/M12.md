## Implementation and adversarial review

The seller web control and the local Worker stop are separate durable authorities. Web pause immediately blocks Core purchase/dispatch while offline and is delivered in a signed Worker welcome before offers. Local pause commits to private FULL-synchronous SQLite before CLI success and continues to block offers during cloud loss, restart and reconnect. The local report is signed and cloud reconciliation is revisioned. A cloud resume never clears a local stop. A seller cannot clear a platform security block; an internal platform-only clearance requires fresh healthy signed telemetry and sends an explicit higher-revision directive. An independent local security finding remains latched. The approved-image and minimum Worker-release checks automatically block new work before the dashboard warning is rendered.

The host-native M12 control synchronizer carries signed heartbeats, local pause state and local job-control reports. It advertises **zero paid execution capacity** because the M13 production job RPC composition is not yet present. M07's dispatch loop was corrected to require a same-cycle acknowledged readiness report for the exact capability version, positive capacity and local unpaused state before accepting an offer. CLI health also marks control-only mode NOT_READY for paid work. This repairs an M07 prerequisite defect without introducing a second execution authority. Web command requests remain PAUSE_REQUESTED until the Worker confirms its stopped container; duplicate local reports are reconciled once, and terminal cancellation/timeout releases reserved credits once through M08.

Seller schedule edits use M09 Core and preserve immutable purchased terms. The browser editor supports bounded weekly windows, overnight ranges, all-day/unavailable days, weekdays copy, IANA timezone, current/next/seven-day preview and capacity limits. Maintenance for a Worker or capability is a pause with an optional known end; the scheduler attempts to lift it only after fresh security and readiness checks, leaving it paused otherwise. Public buyers see a coarse expected maintenance end, explicitly conditional on Worker readiness, rather than the seller's weekly schedule. A capability claiming RESTART_STEP is rejected at candidate publication while the durable checkpoint runtime remains future scope; FULL_RESUME and NOT_SUPPORTED remain truthful.

The dashboard shows independent capability isolation, secret and runtime checks; Worker release/OpenClaw compatibility, Docker/image, heartbeat age, capacity, seven-day runtime/failure metrics and sanitized health events; active jobs first, then history; and M08 ledger-backed earnings plus measured/estimated/unknown provider costs. The current published capability price and fixed seller split come from its immutable version snapshot. Settled buyer sales and marketplace fees require a SETTLE ledger journal and exclude refunded jobs. The UI explicitly says earnings can change after refunds or disputes and never labels buyer gross sales as seller revenue. The completed seller operations view does not repeat the first-publication onboarding. Buyer job status uses the existing sanitized PAUSED/SECURITY_PAUSED mapping. No Worker telemetry is treated as financial truth. Seller job-control and schedule routes require the owning authenticated account and same-origin mutation.

The post-pass audit found and corrected an M07 offer path that could run without same-cycle readiness, duplicate offer handling ordered after capacity, a missing signed local job-control cloud outbox, a missing local security-clear distinction, a misleading control-only CLI health state, missing cloud health-change events, a missing maintenance revalidation path, and an M10 buyer availability time rendered in server UTC rather than buyer-local time. It also stopped RESTART_STEP from being advertised before its checkpoint implementation exists.
