## Adversarial design review before implementation

Threats: key theft and log disclosure; a buyer/seller dual account crossing into Worker identity; concurrent idempotent POSTs spending twice; lost response after successful reservation; webhook DNS rebinding, redirect to metadata/LAN, proxy use, oversized response or secret leakage; delivery process death between HTTP success and acknowledgement; forged/duplicated Worker completion causing a false buyer webhook; test events masquerading as real jobs. Control choices: high-entropy opaque keys and a distinct DB credential class; scopes checked per route; transactionally unique idempotency records with durable operation IDs; Core quote/purchase remains the only money path; job-transition-triggered immutable event outbox; HMAC over timestamp and exact raw body; DNS resolution immediately before a pinned socket with all answers public; redirects treated as failure; bounded, idempotent outbox leasing and attempt records. Tests must try to break each control.

## Implemented boundary

`0023_buyer_api_webhooks.sql` stores key hashes/audit, scoped rate windows, account-wide job idempotency and an immutable webhook event/outbox created in the same transaction as job transitions. `BuyerApiKeyRepository` handles independent key lifecycle and crash-safe stable operation IDs. `/v1` authenticates only buyer bearer keys, calls the M10 buyer/catalog/assets services and lets M09 booking plus M08 credits decide paid admission. Direct file upload uses private object storage, and output downloads reauthorize the buyer on each request. The account page shows a key or webhook secret only when created/rotated.

`BuyerWebhookRepository` encrypts endpoint secrets, leases delivery without consuming a retry before an outcome, retries at bounded exponential intervals, records sanitized attempts and disables exhausted endpoints. The HTTP adapter uses a vetted pinned public IP with original-host TLS verification and no redirects or proxy. The internal cloud dispatcher is secret-authenticated. The Worker RPC route authenticates a device signature before M07 Core accepts, releases inputs, renews leases or finalizes; it invokes M08 settlement/release only after the trusted job state changes. The M08 terminal-job reconciler repairs a crash after a terminal transition.

The scheduler samples each published capability's seller-authorized Core availability once per minute into immutable observations. Seller metrics count observed online/offline/busy/scheduled-offline minutes and explicitly report unobserved periods, plus jobs accepted, queue-full rejects, median wait/execution and disconnect failures. The seller dashboard labels the time series as sampled and never feeds it into public marketplace ranking. Queue-full rejection writes use the attempted quote ID for retry deduplication. This closes §354 without claiming precise continuous uptime from incomplete history.

M13 also corrected two earlier defects: accepted-quote retries could re-finalize an immutable input grant after a successful job booking, and a mismatched signed Worker body returned a generic server error. They now recover the original job without rewriting grants and return an explicit authentication denial. §406 now returns `CAPABILITY_SCHEDULED_OFFLINE` for immediate API jobs outside seller hours with zero credit reservation. A Worker-supplied output-retention deadline is ignored in favor of the server's 30-day policy.

## Adversarial review after implementation

The PostgreSQL/SeaweedFS suite attacks duplicate and aliased idempotency keys, concurrent claims, lost replies, zero credits, final-slot competition, visibility and cross-buyer assets, undeclared fields, forged Worker signature/device/event correlation, result finalization before financial settlement, API rate ceilings, TLS/query-key denial, pause/offline/schedule denial, webhook crash leases, replay, redirects, DNS rebinding and retry exhaustion. Financial and job outcomes remain owned by M08/M07; the API and Worker transport cannot grant themselves execution or earnings. Real Docker/OpenClaw execution, provider parity and physical sleep/crash trials are recorded as component-only evidence until their later acceptance suites run.
