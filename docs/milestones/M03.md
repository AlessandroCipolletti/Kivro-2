## Concise implementation plan

1. Define a strict provider-neutral dependency graph, confidence/requirement/sensitivity/support fields, inference dependency and immutable graph snapshot. Normalize the M02 read-only OpenClaw candidates into **suggestions only**; unknown remains unknown.
2. Implement pure analysis: closure, cycle/conflict detection, required dependency prompts, capability-specific readiness blockers, and permission expansion diffs. Never auto-select a discovered or transitive sensitive dependency. Record explicit seller approvals against a manifest hash.
3. Persist seller draft, selected dependency and consent state with ownership and forward-safe migration. Publish only after explicit approval, real health/security/sandbox tests, payout state, valid I/O/price and immutable version snapshot; fail closed while M04/M07/M08 prerequisites are absent.
4. Build a guided seller flow: explain local execution and cost ownership, scan, select, analyze, review each access/credential/inference choice, test readiness, show price/cost and public contract, preview, then publish. Discovery must not leak personal config or imply consent. Use realistic development fixtures for visual work but keep publication disabled without real evidence.
5. Implement version/visibility contracts separately from availability. Add rollback/diff rules and private grants. Introduce API key, REST, webhook and availability contracts without duplicating Core business logic; complete their runtime behavior when the named later services arrive.
6. Validate with unit/property tests for graph closure/cycles and consent, PostgreSQL authorization/immutability tests, security tests for no implicit access or secret leakage, browser tests for guided flow, and later real Worker/sandbox/provider E2E. Review desktop/mobile UI. Revisit M02 `WRK-0017`–`WRK-0023`, `SEC-0001`–`SEC-0008`, `WRK-0036`–`WRK-0042` as soon as their M03 dependencies arrive.

## Initial increment

Build the provider-neutral dependency graph and explicit-selection/consent decision layer before any publish UI or runtime wiring. This is a real M03 prerequisite; it can be unit-tested without implying that discovery grants permission or that a job can run.

### Evidence to date

- `packages/contracts/src/dependency-graph.ts` defines bounded, strict dependency/inference/consent schemas with reference validation, explicit confidence/support/health, graph edges, and alternative requirement groups. A null inference dependency is valid for a draft but blocks readiness.
- `packages/domain/src/dependency-graph.ts` changes one selection per explicit seller action, detects missing required/alternative nodes, cycles, unsupported or uncertain dependencies, missing inference/credential and failed/unknown health. It verifies per-node consent against a server-derived seller, Worker, version and manifest hash. It does not authenticate an API caller or issue publish permission.
- `packages/openclaw-adapter/src/dependency-candidates.ts` maps file-backed OpenClaw declarations to unselected seller-local graph suggestions. `bins` and `anyBins` remain semantically distinct; alternative binaries require one explicit choice. Environment/config key names are suggestions, never values or automatic grants. Runtime observation, effective OpenClaw inventory and consent UI remain absent.
- `apps/worker/src/import-drafts.ts` stores private seller-local discovery drafts in FULL-synchronous SQLite. Initial imports reject preselected permissions or inference. Explicit selections advance an optimistic revision, log append-only actions, survive restart, reject cross-seller reads and return an idempotent outcome for exact replays. Consent records are append-only and bound to a seller, Worker, version and manifest hash. They are evidence records only; an authenticated seller API and publication validator must still verify them before granting any permission.
- `packages/contracts/src/capability-visibility.ts` and `packages/domain/src/capability-visibility.ts` keep DRAFT/PRIVATE/UNLISTED/PUBLIC access distinct from availability. A direct link never grants PRIVATE access. Version lifecycle permits draft testing and readiness, publication and terminal retirement without mutating a published version snapshot.
- Forward migration `0008_capability_visibility.sql` adds capability visibility, explicit private grants and a separate version lifecycle projection. PostgreSQL triggers reject non-draft visibility without an active published version, PUBLIC without ready payout, unauthorized private grants, active-version retirement and illegal lifecycle skips. The disposable PostgreSQL 16 test `pnpm test:postgres:m03` passed and the forward migration applied to the local database.
- `packages/persistence/src/seller-profiles.ts` creates one DRAFT seller profile for a verified ACTIVE canonical account, serialized by an account row lock. Forward migration `0009_seller_execution_ack.sql` records the execution-model statement version with an append-only acknowledgement; creating a profile never silently grants later resource access. The authenticated `/api/seller/profile` endpoint derives ownership solely from the session, requires same-origin JSON POSTs, bounds the body, rejects unknown fields and returns no-store responses. Real PostgreSQL concurrency, eligibility, cross-account lookup, CSRF, explicit-acknowledgement and idempotency tests pass. The `/seller` page explains local execution, seller-funded model/provider costs, explicit approval and draft status. Its unchecked confirmation is required before continuing. It contains no fake connection/readiness claims or publication action. Chrome E2E reaches it through sign-in, confirms the statement, creates the profile, and checks the protected route after sign-out; desktop and 390px mobile screenshots were reviewed. A mobile sign-out visibility bug found during that review was fixed.
- `packages/contracts/src/capability-package.ts` defines a strict Worker-local draft package with the complete dependency graph, internal policy, manifest, I/O, pricing and only inference credential **references/hash**. `buildVersionCandidate` derives the sanitized cloud candidate and canonical package/graph hashes from that one package, rejecting inconsistent IDs/config. This is a pure immutable snapshot boundary; local package persistence and final publish attestation remain open (`DEC-IMPL-005`).
- `packages/policy-engine/src/permission-diff.ts` compares exact internal resource/credential references, skill hashes, tools, network routes, resource grants, selected graph nodes and inference configuration. The public category summary alone would miss a changed file or destination. Unit tests prove those expansions are detected, while UI review and publication enforcement remain open.
- `tests/dependency-graph.test.mjs`, `tests/openclaw-discovery.test.mjs`, `tests/import-drafts.test.mjs`, `tests/capability-visibility.test.mjs`, `tests/capability-version.test.mjs`, `tests/permission-diff.test.mjs`, `tests/sql/m03_visibility.sql`, `tests/seller-profile-local-integration.mjs`, and the authenticated/browser flows cover the incremental behavior. `pnpm typecheck`, `pnpm lint`, `pnpm test` (94 tests), `pnpm test:postgres:m03`, `pnpm test:seller:local`, `pnpm test:auth:local`, `pnpm test:auth:browser`, and the Next production build passed after migration 0009.
