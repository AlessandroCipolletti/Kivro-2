# M16 OpenClaw interface review

Reviewed 2026-10-07 against the current official [agent CLI](https://docs.openclaw.ai/cli/agent), [configuration](https://docs.openclaw.ai/cli/config), [skills CLI](https://docs.openclaw.ai/cli/skills), [sandbox overview](https://docs.openclaw.ai/gateway/sandboxing), [Docker backend](https://docs.openclaw.ai/gateway/sandboxing/docker-backend), [sandbox CLI](https://docs.openclaw.ai/cli/sandbox), [exec tool](https://docs.openclaw.ai/tools/exec), and [trust-boundary explanation](https://docs.openclaw.ai/start/why-openclaw). Kivro executes the pinned OpenClaw `2026.8.2` image and tests its effective configuration; unversioned live documentation is a compatibility input, not permission to silently change the tested image.

The current agent CLI documents that an `agent exec` without configured sandbox can execute on the Gateway host. OpenClaw also states sandboxing is off by default, the Gateway itself remains host-side, and native plugins are not sandboxed. Kivro therefore checks the effective mode-all contained backend, disabled elevation, exact tool policy, approved image and Docker settings before a job starts. A missing or changed prerequisite stops the job; it does not choose host execution. `tests/docker-openclaw-exec-local-integration.mjs`, `tests/docker-openclaw-image-local-integration.mjs` and `tests/openclaw-image-approval.test.mjs` are the executable evidence for the pinned runtime.

The current Docker reference describes `network: none`, read-only root, dropped capabilities and no host Docker socket. Kivro's outer per-job Docker boundary independently enforces and inspects those settings. The M16 sandbox canary probes public IP, localhost, LAN and metadata targets, while the pinned OpenClaw test checks an unmounted host sentinel and metadata denial. These are local-component proofs; the paid published-capability red-team gate remains open.

The skills CLI currently documents `list`, `info` and `check` as a Gateway-authoritative inventory. Calling that path may initialize or alter a personal Gateway state, so Kivro discovery remains read-only filesystem/config/skill-metadata inspection in `packages/openclaw-adapter`. It reports uncertain candidates rather than claiming full Gateway inventory. Discovery never grants use; explicit seller selection and reviewed immutable publication are required. The seller publication path is still absent and blocks the full skill-consent acceptance gate.

The live metadata-snapshot probe was repeated on the active development machine. It sometimes passes with 57,830 scanned entries and 57 skill candidates, and sometimes detects changes to the active OpenClaw `tmp` directory metadata and `agents/main/agent/codex-home/logs_2.sqlite-wal` during the scan. The adapter source opens files with `O_RDONLY | O_NOFOLLOW` and uses metadata/directory reads only; the observed drift is consistent with concurrent personal-state activity, but this experiment cannot attribute writes to a process. `PRD-0010` remains open until a quiesced real installation or attributable filesystem trace establishes the complete live non-mutation proof. No path is silently excluded from the test to make it pass.

The config CLI documents a read-only mode and validation, but a successful schema check does not prove provider parameters, secret resolution or runtime isolation. Kivro does not treat config validation as sufficient readiness; it uses exact image approval and a runtime self-test. Live docs may evolve after the pinned image; changing versions requires a fresh source diff, image build, compatibility test, security test and approval record.
