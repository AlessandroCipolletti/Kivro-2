# M15 operations and privacy runbook

## Authorities

- The Core job/lease repository remains the only dispatch authority. An operator dispatch halt is checked under a PostgreSQL row lock in every offer transaction. The control row missing or unreadable blocks dispatch.
- M08 ledger and financial reconciliation remain the only payment authorities. Worker output cannot settle earnings. Result files are copied to cloud-owned private keys, rehashed, type-checked and scanned before a job may enter COMPLETED.
- Operator sessions require an active, email-verified account with an explicit `operator_grants` row. Buyer/seller roles alone confer no operator rights. A database administrator can bootstrap or revoke a grant with `DATABASE_URL=... pnpm operator:grant -- grant|revoke ACCOUNT_UUID`; do not put this connection string in shell history or logs.
- `GET /api/operator/dispatch|metrics|reports|job/{id}/audit` and POST dispatch/suspend/worker-clear/report-state/deny-pattern actions return only bounded codes and identifiers. POST requires same origin. Reports move `OPEN` → `REVIEWED` → `CLOSED` with coded decisions. Security-block clearance delegates to the M12 fresh signed Worker-readiness check.

## Abuse and investigation

- Shared Core quotes allow at most 60 new quotes per buyer per minute. Shared Core booking limits are 20 jobs per buyer per hour, $500 in job reservations per rolling day and 10 active jobs. Limits are checked under a buyer account lock before credit reservation so concurrent API/web/Agent purchases cannot evade them. An idempotent replay of an existing booking remains possible. These are conservative private-alpha defaults; changing them is an explicit operator policy decision.
- Buyers and sellers can report an owned job using a reason category. Reports contain IDs and categories, never prompt text. Operators can inspect open reports and suspend accounts/capabilities, revoke a Worker, add a bounded normalized deny pattern, or halt all dispatch. A revoked Worker must be paired again; generic operator resume cannot restore its credential. A new pattern is evaluated during authoritative input-manifest finalization for web, API and Agent jobs; it never substitutes for sandbox permissions.
- Job transitions, financial journals, Worker operational events and platform control changes provide a structured investigation trail. Operator job audit emits status/actor/correlation IDs, not inputs, files, credentials, provider transcripts or raw report descriptions. Metrics use authoritative rows and a named 30-day window; a missing sample remains unknown rather than invented.
- For suspected credential or Worker compromise, halt dispatch first; suspend affected account/capability/device; verify Worker revocation and active lease status; reconcile the M08 ledger; inspect the sanitized audit; preserve evidence under the private retention policy. Resume only after security/readiness checks. Never edit job or financial rows manually to repair routine failures.

## Files, scanner and health

- ClamAV is a required prerequisite for delivering generated files. Set `KIVRO_CLAMAV_SOCKET` to a private Unix socket or `tcp://127.0.0.1:13310` for local Compose only. The latter is bound to loopback, never the LAN. The Worker obtains one short-lived signed PUT for each exact job/execution/attempt/lease/output field and uploads into a private staging key. Cloud copies the bytes into a new key never disclosed to the Worker, verifies size/hash/MIME/extension and scans that copy before delivery or settlement. A scanner error, timeout, malware verdict, object mismatch or unissued key keeps the result unfinalized. Unsafe output terminally releases credits; the full paid path still needs M16 E2E. The scheduler removes staging objects only after issued PUT URLs have expired, and never removes the delivered copy.
- Local Compose starts the digest-pinned official ClamAV 1.4.6 image with its virus database on a persistent volume. The official tag has no ARM64 manifest; Compose selects `linux/amd64` for local Apple Silicon emulation. Its stream/file/scan limits cover the 1 GiB platform output ceiling and `AlertExceedsMax` rejects unscanned oversized content. Production scanner deployments must enforce at least the same ceiling or a stricter published file ceiling. Signature download and scanner readiness may take time on first start. `GET /health/live` proves the process handles requests; `GET /health/ready` checks PostgreSQL, private object storage and scanner availability, returning only READY or NOT_READY.
- The Worker opens no local management HTTP listener. Its health/doctor commands use private SQLite state and host-local checks; future local UI control must bind to loopback or IPC and require authentication. For local readiness evidence run `pnpm local:auth:up`, `pnpm local:auth:migrate`, then `pnpm test:health:live`; the test requires real PostgreSQL, private storage and ClamAV. `pnpm test` separately verifies the fail-closed response without these prerequisites.

## Privacy and prelaunch gates

- Buyer input runs on an independent seller machine inside the per-job sandbox; the seller Worker can process authorized inputs. Platform object storage temporarily retains inputs/results; My Jobs displays the result deadline. The buyer capability page presents declared external processors, with unknown declarations shown as blocking. No arbitrary result URL is fetched automatically.
- Before public seller onboarding, complete the §91 security gate, external review or explicit private-beta risk acceptance, legal review of terms, acceptable use, seller/buyer agreements, privacy and data processing, KYC/payouts, taxes, chargebacks, IP/confidentiality, prohibited services and applicable export/sanctions rules. Private alpha should limit financial volume and access until resolved. These are launch gates, not claims that legal review happened.
