# Buyer and seller web app

The M02 authentication route and its PostgreSQL adapter are implemented under `src/auth/` and `app/api/auth/`. Email registration, verification, login, reset and logout pass backend and automated Chrome browser tests using local PostgreSQL and Mailpit. Sign-in, account creation, verification guidance, recovery, and account screens are present. A manual local browser review confirmed desktop and mobile layouts. Real Google callback, account deduplication/linking and the complete failure-state E2E matrix remain open.

The auth audit records account, identity, password, and session changes transactionally in PostgreSQL, plus route/status outcomes for sensitive HTTP flows. Its table has no credential, email, IP, token, or URL fields. Audit insert failure suppresses a newly issued auth response. Audit retention and broader attack/failure testing remain open.

M03 adds the protected `/seller` entry and `/api/seller/profile`. A verified active canonical account can create one draft seller profile after explicitly confirming the local-execution and seller-cost statement. The acknowledgement is versioned and append-only in PostgreSQL; it does not grant capability permissions. The seller page does not claim Worker pairing, readiness or publication. The full import wizard and consent/publish APIs remain open.

Better Auth's user ID is the canonical Kivro `accounts.id`; provider accounts live in `account_identities`. Never add a second auth user table. Production requires explicit auth secrets, an encrypted email outbox key, Google identity credentials, and HTTPS. There is no development bypass for verification or paid actions.

## Buyer marketplace (M10)

`/discover` lists current PUBLIC published capabilities with text search, categories, price/rating/output/runtime/online filters and sorting. `/capabilities/[slug]` shows the current authoritative version, input/output contract, price, seller-approved examples, reviews, permission summary and M09 availability. UNLISTED capabilities remain direct-link only; PRIVATE capabilities require an explicit grant. `/sellers/[id]` shows only public published supply. Authenticated buyers use `/buyer` for My Jobs, Favorites, Recently Used and Credits, and `/buyer/jobs/[id]` for immutable purchase terms, persisted status, validated results, private retained downloads, problem reports and current-terms Run Again.

The run form uses the versioned input contract. The authenticated API signs a short-lived, private object-storage staging upload; browser bytes go directly to storage with incremental SHA-256, while the API receives metadata. Finalization validates both staging and server-side-promoted final objects before an input becomes READY. A still-valid upload URL cannot overwrite the final job input. Buyer preflight then obtains a short-lived Core quote. Purchase revalidates that quote and M09 booking atomically reserves M08 Credits. A lost browser response is recovered using the same job/reservation IDs so it cannot silently purchase twice. The Worker is not involved in credit authorization. Missing lease, object-storage or Stripe prerequisites fail closed for actions requiring them; public catalog browsing remains available from PostgreSQL.

After the root local setup (`pnpm local:auth:up`, `pnpm local:auth:migrate`, web server and mailer), seed a real published capability/Worker readiness and test Credits through the existing development fixtures. Run `pnpm test:postgres:m10` for disposable database state/authorization tests and `pnpm test:browser:m10` for a disposable PostgreSQL + pinned SeaweedFS + Mailpit Chrome journey; no production billing credentials are needed for those tests. The browser test emits `test-results/m10-*.png` screenshots for desktop/mobile inspection. Live Stripe test-account checkout, full paid browser→Worker→sandbox→result delivery and formal public REST/MCP APIs remain later acceptance gates tracked in `docs/verification-backlog.md`.
