# Seller Experience Specification

## Product principle

A seller should not need to be a DevOps engineer to safely sell an
OpenClaw capability on Kivro.

## First publication

Connect Worker → discover candidate skills/tools/resources → explicitly
choose what to expose → optionally accept AI drafting help → review
dependencies and exact permissions → configure local credentials →
preview as buyer → satisfy deterministic readiness → set
price/availability/capacity → publish.

## Daily operations

Seller sees running work, capability health, precise unavailability
reasons, earnings, provider costs and profit estimates. Pause,
maintenance and capacity controls are operational and do not require
republishing.

## Safety

Discovery never equals consent. AI never authorizes. Secrets remain
local/approved secret storage. Buyer identity is minimized. Cost
guardrails protect seller-funded inference. Repeated deterministic
failures can auto-pause new sales with an explainable recovery path.

## Versions

Published versions are immutable. Draft changes show semantic diffs,
especially permission expansion. Bad versions can stop receiving new
work and an eligible previous version can be restored without rewriting
in-flight/history.

## Identity and growth

Public marketplace brand may differ from private KYC identity.
Reputation signals are explainable enough to improve legitimate quality.
First-publication and first-sale journeys explain readiness, economics
and payout.

## Future structure

The domain supports multiple Workers per seller from greenfield even if
MVP UI exposes a simpler subset.

## Cross-provider rule

All seller business semantics pass the same conformance suite on Netsons
and AWS.
